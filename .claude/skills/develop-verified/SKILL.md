Run in the MAIN conversation as the accountable **technical lead**, never in a fork. Mission: $ARGUMENTS. Follow CLAUDE.md, approved `docs/` contracts, the implementation and qualification plans. This skill changes the **development workflow only**, never authorizes product scope changes, waives acceptance, merges a PR or starts the next milestone. The lead independently ACCEPTs, REJECTs or DEFERs fallible agent advice; no reviewer is an approval authority. Produce a review-ready PR if objective evidence is complete, an honestly marked draft if incomplete, or HOLD for a real blocker. Work locally; ask before installing outside the repo. Keep the existing Beads item, chronological worklog and PR; no additional tracker, app/router debug logging or credential exposure.

## 1. Target and finite acceptance contract
- Inspect actual branch/status/user changes, remote base and true merge-base (never stale local main), existing PR and its **material outstanding** review bodies/inline threads/discussion, latest merged instructions, applicable approved scope, Beads issue and relevant tests. On a recheck, use the prior worklog/dispositions to avoid re-reading/re-litigating the entire historical review timeline; retrieve new or materially changed feedback and its original context. Do not overwrite uncommitted user work.
- Distinguish `NEW_FEATURE` (one approved milestone) from `PR_RECHECK` (correct the SAME open PR; no new feature/PR). Before coding, state a compact **CORRECTION/ACCEPTANCE CONTRACT**: finding IDs, normative invariant, positive and negative contrasts, minimal evidence needed, explicit done condition. For a new feature, use the approved milestone acceptance/invariants instead.
- The contract is finite, but a **demonstrated mandatory violation or fix-induced regression** still needs resolution. Do not convert speculative adjacent suggestions into acceptance criteria. Only owner arbitration changes normative scope. If a proposed implementation cannot satisfy the contract, address the cause or declare a named unsupported case where the normative contract permits it; never fabricate a passing oracle.

## 2. Start work without a mandatory plan barrier
- The lead reproduces the decisive defect or identifies the necessary observable behavior, then **starts implementation once the contract is clear**. A plan reviewer is OPTIONAL: request an independent critique asynchronously for uncertain architecture, contested contract or high-risk strategy. It is advice, **not a prerequisite to edit**; consume a useful timely report before freezing the candidate. If absent, record that limitation and proceed on accountable judgment. Do not launch a plan critic just to satisfy a ceremony.
- Implement the smallest **sufficient**, maintainable change that fixes the general invariant and its few discriminating neighbors. Keep source C/SDD/oracles immutable. Do not add unrelated features, abstractions or verbose documentation.
- The lead alone decides ordinary technical trade-offs, including whether a critique is valid. For each material finding record `ACCEPT` (confirmed mandatory violation/regression), `REJECT` (falsified, redundant, optional or out of scope with evidence), or `DEFER` (real but outside this bounded contract, or unproven with an explicit bounded probe/limitation). A confirmed mandatory blocker **cannot** be deferred into a false READY. Multiple agents agreeing do not replace proof; one justified rejection needs no consensus loop.

## 3. Challenge early; use the fewest agents
- **DEFAULT:** one lead is the code/test/PR writer; use fresh independent subagents only where they add a distinct critical viewpoint. Start a `test-challenger` **early**, in parallel with the first implementation or first small testable candidate, for changes risking false oracles, types, C/SDD interpretation, tool/result classification, persistent state or safety invariants. Give it the normative invariant and a small stable snapshot; it derives counterexamples independently and returns the most decisive ones. Launch it at most once per correction contract/materially changed risk, not after every patch or after the complete Docker campaign. For low-risk documentation-only changes, skip with reason.
- An `implementation-reviewer` is OPTIONAL for architectural or contract uncertainty; do not require both a plan checkpoint AND a candidate checkpoint for a local correction. If used, challenge one stable fingerprint, not an actively edited file. The early challenger may replace the live candidate critique when their risk coverage overlaps. A continuous `convergence-guardian` and a dedicated `evidence-keeper` are **not default participants**.
- Agent Teams may be used when actually available and useful; otherwise isolated one-shot subagents suffice. Never assume flag, delivery or provider/model routing succeeded. For each delegated critique supply scope, frozen inputs/revision, bounded task/turn budget, report location if needed and explicit output schema. Use ignored `.claude/.runtime-reports/<session-id>/` only for essential reports; reports written atomically with checkpoint ID and fingerprint. Native messages are hints. Prefer the finished report/result; check once at a meaningful join point rather than repeatedly polling or pinging; a missing pop-up or IDLE state is not failure. One bounded recovery attempt only for a **required** result; optional advice must not block progress. Never simulate missing reports.
- The lead is sole owner of Beads/worklog by default. Delegate to keeper only for a substantial, truly independent documentation workload. If delegated, require explicit `ACK ACCEPTED` before any keeper write and `RELEASED` or confirmed termination before lead takeover; never allow competing writers. Record meaningful states once, near publication, not status chatter.

## 4. Evidence ladder — validate the right thing, once
- **During editing:** run a handful of targeted, discriminating tests and negative/positive contrasts. Prefer a fail-before/pass-after regression where meaningful; never encode the defective implementation as the expected oracle. Do not repeatedly run whole suites on intermediate revisions.
- For a **C generator change affecting types, emitted calls, pointer observation or assertions**, the acceptance contract MUST request evidence at appropriate layers: (a) shape of generated text, (b) **compilation against the actual compiler/Unity/Ceedling profile**, and (c) execution against a tiny correct and, where material, incorrect SUT to distinguish a faithful oracle. A Python string equality alone does not prove emitted C compiles or asserts the right object. This is a workflow evidence rule, **not authorization to expand product code or implement a separate generator test framework**. Reuse existing tools/fixtures where possible; unsupported cases must yield a named limitation rather than a fabricated verdict.
- For other material boundaries, select similarly discriminating integration proof (e.g. state transition, real runner/environment, mixed failure precedence) required by AP-01/02/03. Run real host/WSL/Docker/LLM paths when relevant; mocks are not evidence of a real call. Do not turn every neighboring type or edge case into a full matrix.
- **On a stable candidate**, run only the applicable full offline/Docker/qualification campaign (one owner: lead or one task-runner) and capture exact command, underlying process exit code, environment/config, input/revision hashes, outputs and artifacts. Use native background Bash for a single long command; a task-runner only for useful parallel *multi-step* work. Capture output in a file and preserve the exit code (`pipefail` when piped); do not repeatedly start commands or pipe their result through `tail` in a way that hides failure. Track each background task ID, collect each result once, and never launch a duplicate suite while one is still running. No reviewer/keeper/guardian/challenger runs full campaigns.
- **Reuse completed evidence** on identical effective code, relevant test/config inputs and environment; run only affected tests after a change. Distinguish executable/test-input modifications from worklog, PR text or comments: a metadata-only edit does not invalidate a verified code/test fingerprint or require all suites again. Record changed hashes and applicability, never claim an outdated result proves changed behavior.

## 5. Convergence control — trigger on evidence, not ceremony
- Before publication, the **lead** performs lightweight deterministic scope/diff hygiene versus the true merge-base and reads existing evidence. Invoke a fresh `convergence-guardian` ONLY when there is real drift, disproportionate complexity, repeated corrections, stalled progress, disputed scope, or stale contradictory evidence. It reviews diffs and existing proofs; it never reruns whole suites or creates requirements. No unconditional post-plan or prepublish guardian barrier.
- If **two distinct corrective strategies** fail for the same defect class, STOP local patch/review cycling on that class; restate the root invariant, evaluate a simpler architecture or explicit unsupported-case limitation if permitted, and select a bounded new strategy or seek owner arbitration for genuine scope/product decisions. This is an escalation signal, **not** permission to ignore a confirmed mandatory violation.
- One material finding, one disposition and necessary proof; repeated findings without new evidence do not reopen work. A reviewer hypothesis alone does not restart the workflow. A late new **proven mandatory regression** does reopen the affected code and focused evidence, not every historical review.

## 6. Freeze once; run one bounded independent final review
- Finish relevant code/tests/docs/Beads decisions and join required jobs. Freeze the candidate using true remote merge-base, base/head SHAs, changed tracked/untracked **effective input hashes**, relevant evidence/config hashes, PR number and material review snapshot. Give the reviewer the prepared PR summary, correction contract and compact real test results. Reviewers operate on a stable snapshot/worktree and cannot write tracked code or evidence.
- **MANDATORY for every `/develop-verified` run, including docs-only:** invoke **ONE** fresh isolated, non-Team `contract-reviewer` using `/verify-feature` **OR** one equivalent direct Task invocation, **never both by default**. Request a short structured fingerprint-bound verdict (`READY | CHANGES_REQUIRED | NOT_VERIFIED`) within the turn budget. Prioritize the finite contract, source-level oracle validity, changed lines, affected contrasts and accepted mandatory evidence; do not explore the whole product or rerun full campaigns. If the chosen invocation returns no usable verdict, try **one** direct isolated fallback with the same evidence/fingerprint and an instruction to return a partial structured verdict immediately; do not resume an endless investigation. If still unavailable, mark independent evidence NOT_VERIFIED.
- Review opinion is advisory. Lead independently ACCEPT/REJECT/DEFER each material objection with a contract/proof rationale. `PUBLISH_READY` requires complete objective mandatory acceptance evidence, no demonstrated unresolved mandatory defect, and completed usable independent review; a reviewer `CHANGES_REQUIRED` does not veto a technically refuted claim. Missing mandatory proof/review or a real blocker permits only explicitly incomplete `PUBLISH_DRAFT` or `HOLD`; never invent a READY verdict.
- A material code/test/contract change invalidates applicable test evidence and the prior final verdict; after focused correction and refreeze, obtain ONE fresh final review on the new candidate for READY. Non-semantic docs/Beads/PR export updates after a verified frozen code candidate do not themselves trigger re-running unchanged executable checks; identify precisely which review claims remain applicable and re-review changed **normative** content when necessary. Do not let advisory reviewers restart broad cycles.

## 7. PR delivery and stopping boundary
- Update the **same** Beads item/worklog/PR for PR_RECHECK; no replacement PR, additional tracker or repeated verbose reports. Record key command/exit/proof references, lead dispositions, deferred limitations, and accepted scope. Hygiene-check changed files, exports and logs for credentials, private paths and personal data (AP-05); never edit the independent risk register. Verify branch and clean/safe status. Batch final documentation/export and commit/push instead of repeated cosmetic commits when practical.
- Lead chooses `PUBLISH_READY | PUBLISH_DRAFT | HOLD`. For READY, publish/update review-ready PR only after evidence and independent critique; check actual fast CI and address genuine failures. For DRAFT, explicitly disclose known defects/unproven checks and do not ask for merge. For HOLD, give precise blocker. An explicit user request to STOP/publish freezes new speculative reviews, but never waives objective mandatory criteria or authorizes a false READY.
- Respect the repository merge boundary: **do not merge or begin the next milestone without the user's explicit instruction.** Finish by reporting PR URL/head, lead decision, actual checks and CI result, material reviewer dispositions, unresolved limitations and the follow-up scope. Shut down live teammates and join required jobs. No fake success, stale fingerprint, or orphan background work.

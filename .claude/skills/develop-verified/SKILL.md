1. Changes to this contract require either a confirmed in-scope regression caused by the fix, a newly demonstrated mandatory blocker, or explicit owner arbitration; speculative suggestions are not automatically added. For NEW_FEATURE establish the same bounded requirement/invariant/acceptance plan. Do not confuse green tests with acceptance.

2. PARALLEL TEAM / EXCLUSIVE WRITER: With Agent Teams enabled, start named implementation-reviewer and evidence-keeper teammates and confirm actual spawn/native messages. If owner remains ambiguous, pause Beads/worklog writes and mark evidence gate BLOCKED instead of racing. When no keeper started, lead owns evidence from the outset. Keeper checks provenance but NEVER runs tests. If Teams unavailable, use fresh sequential critique, disclose degraded parallelism and never simulate communications.

3. DEVELOP / RECHECK: Make the smallest SUFFICIENT maintainable change under approved contracts and existing architecture. Independently reproduce each material PR finding, identify its violated invariant and a SMALL set of discriminating neighboring contrasts, then implement/test the general fix. Classify RESOLVED/PARTIAL/UNRESOLVED/NOT_VERIFIED/DISPUTED with evidence. Triage every NEW reviewer suggestion BEFORE editing: (a) demonstrated violation of an approved mandatory contract or a regression directly caused by this change -> resolve/block; (b) plausible but unproven -> targeted probe or NOT_VERIFIED, not speculative coding; (c) ambiguity/out of scope -> surface for owner arbitration, do not silently expand the mission. Do not use a new reviewer hypothesis alone to restart the complete workflow. For a new milestone, implement the complete user-visible feature (not artificially split). Detect divergence between docs, arbitration, Beads and changed main; surface genuine scope arbitration. Keep source C/SDD/oracles immutable. Lead or ONE explicitly delegated task-runner owns each full local pytest/build/Docker/qualification campaign; reviewers, guardian, challenger and keeper must not duplicate those runs. Execute targeted tests while fixing findings, then the applicable complete campaign on a stable candidate, not after every trivial edit. Reuse completed results for unchanged effective inputs/revision, environment and command; re-execute affected tests only when invalidated by later changes or needed to prove another contract. Run real WSL/Docker/LLM integration when AP-02 requires it; mocks cannot prove a real call. Capture exact command, original process exit status, revision/input hashes, relevant outputs and artifacts (a `pytest | grep` pipeline without pipefail is NOT reliable pass evidence). No feature/source change to silence a review. Send compact evidence references and finding dispositions to the ACKed keeper or sole lead fallback.

4. CONVERGENCE CONTROL: Automatically invoke a fresh unnamed convergence-guardian subagent after the plan, on major architecture/scope/diff changes, after repeated unsuccessful corrections or disagreement, and before PR publication. It audits approved scope against the true merge-base-to-head diff, unnecessary abstractions, redundant tests and stalled progress from existing evidence; it does NOT run full pytest/Docker/build suites. It returns grounded minimal actions rather than edits. The lead tests/refutes findings; do not rubber-stamp or let the guardian create requirements. Do not spawn a continuously polling guardian. If the SAME defect class causes material regressions after TWO distinct correction strategies, STOP further local patch/re-review iterations on that class. Compare the root invariant and a simpler architectural alternative, including an honest explicit unsupported-case limitation where allowed by the approved contract. If a bounded strategy cannot be justified, report BLOCKED and request owner arbitration; never paper over known mandatory defects or silently drop acceptance requirements. A new guardian report is advisory and must not itself spawn another reviewer/qualification cycle. If an unchanged finding recurs without new evidence, report its status rather than re-probing. Aim for minimum justified DIFF, not minimum lines or omitted necessary tests/docs.

5. LONG COMMANDS VS INDEPENDENT TASKS — CHOOSE THE LIGHTEST CONCURRENCY:
- First ask: while this operation runs, can the lead make useful progress on DIFFERENT work without depending on its result, and without shared-write/input races? Do not create artificial work to justify parallelism.
- SHORT / prerequisite command: execute normally. LONG straightforward command (test/build/install/probe/etc.): use Claude Code native Bash `run_in_background` / task ID by default, even when no teammate is warranted. Continue useful independent work if possible; otherwise await completion. Retrieve the actual exit/status/output before using the result; background launch is NOT acceptance.
- Only for a LONG, BOUNDED, AUTONOMOUS task with genuine independent overlap AND meaningful multi-step execution/investigation/diagnosis beyond a single command: optionally delegate to ONE background `task-runner` subagent via .claude/agents/task-runner.md when a final report suffices; use a named Agent Teams teammate only when interim messaging or coordination is truly necessary. Examples: sequenced integration campaign, bounded independent investigation, multi-command environment analysis, build qualification. Do NOT delegate just to have another agent watch a shell process or duplicate reviewer/keeper roles. No continuously polling worker. If Agent Teams is unavailable, an ordinary background subagent may still be used if available; otherwise use background Bash. Never fake parallelism.
- For either mode, prevent conflicting writes and stale inputs. Use stable revision/file hashes; snapshot only when inputs may change while the task executes. A commit/worktree is one option, not a universal prerequisite: an explicitly captured copy may include relevant uncommitted files. Use separate scratch outputs/containers; do not modify tracked product files from the worker. Lead remains sole implementer and can change independent files, but must invalidate/re-execute affected checks on the final candidate.
- Synchronize all mandatory background task IDs and delegated results before evidence/final review; record completed outcomes and exact input versions with the ACKed keeper or confirmed sole lead fallback, never both. Failed, blocked or obsolete mandatory work cannot be treated as passing. Respect host/secret boundaries and resource limits; no new daemon, result tracker, CI job or automatic merge.

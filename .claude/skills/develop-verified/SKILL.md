Run in the MAIN conversation as the **coordinator**, NOT as the code writer. Mission: $ARGUMENTS. Approved docs and milestone define the WHAT/Definition of Done; Beads records durable execution. This skill coordinates development only: no scope expansion, acceptance waiver, automatic merge or automatic next milestone. The coordinator owns priorities, Beads/worklog/PR, review/test scheduling, integration and publication decision. For implementation delegate to the `developer` agent (one by default); if delegation is unavailable, disclose BLOCKED/degraded mode and request an explicit fallback decision rather than silently becoming the developer. Work project-locally, protect user changes, credentials, C/SDD/oracles and the risk register.

## 1. Preflight, acceptance and backlog
- Check branch/status, uncommitted work, remote target, true merge-base, existing PR and **material outstanding** review bodies, inline threads and discussion; reconcile latest merged `CLAUDE.md` **and applicable `.claude/skills/` / `.claude/agents/` workflow instructions from `main`** with the current branch before delegation (especially an existing PR branch), Beads (`bd prime/ready/list/show`), worklog, applicable docs and evidence. Sync without losing user changes; disclose if the running session cannot load the updated workflow. `NEW_FEATURE` = one approved milestone; `PR_RECHECK` = the SAME open PR, its previous dispositions and newly relevant feedback. Do not re-litigate an unchanged review history.
- Establish a **finite acceptance contract**: approved outcomes, critical invariants, named findings (for recheck), explicit done/negative and positive contrasts, and mandatory evidence. Only owner arbitration changes normative scope. Record criterion → evidence or NOT_DEMONSTRATED in the existing Beads feature item.
- Act as **sole Beads/task scheduler**. Translate the approved plan into a FEW coherent implementation lots, each covering the coupled surfaces of an invariant, its dependencies, focused checks and finish condition. Keep Beads the ONLY durable backlog; native Claude Code Tasks are optional in-session scheduling, not a parallel backlog. Do not create a Beads issue per review comment, test or micro-fix; merge duplicate findings by root cause, split oversized/blocked lots only when this improves progress.
- Use a `planner` **conditionally** for uncertain architecture, large dependency changes, complex multi-lot decomposition or after two distinct failed strategies. It proposes the smallest useful plan; only the coordinator accepts and writes/updates Beads. No synchronous plan-review barrier on a clear local fix.

## 2. Star-shaped communication and technical authority
- **All specialist missions and results route through the coordinator**. Planner, developer, reviewers, challenger, runner and keeper never send instructions, findings, priorities or task changes to one another, never self-claim or reprioritize shared tasks, and never update Beads/PR/worklog unless explicitly given exclusive record-writer ownership. Give each agent the coordinator as its ONLY report/message recipient; do not ask agents to debate or reach consensus. If native Team messaging bypasses this rule, treat the bypass as an untrusted observation and re-route it; prompt constraints alone are not security enforcement.
- Each mission names `MISSION_ID`, Beads item/lot, goal and approved contract, revision/snapshot and relevant input hashes, allowed files/actions, bounded budget, report destination and DONE/FAILED/BLOCKED/NOT_VERIFIED output. Preserve reviewer raw findings and proofs; the coordinator triages against current work, not a reviewer-to-developer interrupt.
- **Developer owns technical implementation strategy** in its assigned isolated worktree/files and targeted tests. It may independently ACCEPT, REJECT or DEFER technical suggestions with evidence and recommend a different approach. The **coordinator alone** accepts backlog/priority changes and decides whether a material reviewer claim affects the approved DoD. REJECT needs evidence; DEFER cannot hide a demonstrated mandatory blocker as READY. No committee/voting veto. Developer does not directly schedule a full campaign, summon reviewers or publish a PR.
- Normally ONE code-writing developer in one worktree. Concurrent developers only for demonstrably disjoint file/working-copy ownership and isolated build outputs; coordinator integrates. Reviewers/guardian/challenger are read-only with at most a few distinct isolated probes. No two writers modify a shared worktree, build directory or persistent state concurrently. The coordinator normally owns Beads/worklog; for substantial record work, the existing evidence-keeper protocol requires ACCEPTED/RELEASED and confirmed exclusive handoff.

## 3. Event-driven scheduling, agent liveness and revision validity
- Start developer promptly when the contract is clear. Trigger early `test-challenger` for substantial oracle, C type, persistence, scope or outcome-classification risk. Optional implementation reviewer critiques one **stable** slice fingerprint while developer can advance independent work. A guardian is **conditional** on observed drift, stall, overengineering, repeated same-class defects or stale/conflicting proof; no perpetual guardian/poller. Specialist critiques are advisory progress signals, not serial approval gates.
- **Monitor active missions at actual join points**: after dispatch and at each useful task completion, reviewer report, background test result, blocking change, or before final freeze, inspect native Agent/Task state, assigned report file and mission fingerprint. A teammate becoming IDLE is normal; it does NOT establish completion or failure. An absent notification does NOT establish a missing report. Check the report first, then the native state/inbox; avoid repeated polling while useful independent work exists.
- For a live Team mission, the coordinator MAY write an ignored session-local receipt under `.claude/.runtime-reports/<team-name>/missions/<teammate-name>.json` containing `mission_id`, `fingerprint`, `report` (project-relative) and `active: true`; teammate writes an **atomic** report whose first lines include `MISSION_ID:`, `FINGERPRINT:`, `STATUS: COMPLETED|FAILED|BLOCKED|NOT_VERIFIED`. The PROJECT-level `TeammateIdle` hook (`.claude/settings.json`, inherited by teammate sessions when project settings load) checks the receipt/report and gives **at most one** missing-report nudge per assigned mission; it neither polls nor guarantees delivery. Use the actual Team name, and a shared project root: an isolated worktree's different root may make the hook unable to see the receipt. Update/retire the receipt when reconciled; the optional native Task `Proof-file:` check remains supported. Only essential ignored scratch receipts, never a second durable tracker.
- If required output is still absent after report/state inspection, send **one bounded coordinator-origin retry or resume**, referencing the SAME mission/fingerprint and asking for an immediate partial status. If delivery still fails, terminate/confirm the worker state, record NOT_VERIFIED, and use **one** isolated replacement when necessary; otherwise HOLD or PUBLISH_DRAFT. Optional opinions never block. Do not repeatedly wake IDLE agents, duplicate assignments or silently assume a crashed agent is done. A hook cannot monitor a stalled process that never reaches an idle/stop event; coordinator must join/check it. Verify that skill hooks actually apply to Team teammates under the installed Claude Code/CCR mode; if not, the coordinator uses native handbacks and explicit checkpoint checks.
- A reviewer finding includes scope, severity, violated approved contract, observed-versus-expected evidence, the exact reviewed fingerprint and minimal probe. Coordinator maps it to a Beads lot; `ACCEPT` grounded blockers, `REJECT` falsified/redundant/speculative/out-of-scope with reason, `DEFER` only legitimate future scope or unproven bounded checks. Do NOT automatically interrupt developer; reprioritize immediately only if a proven blocker makes its current work wasteful/unsafe, otherwise at its next coherent checkpoint. Review on A remains valid ONLY for unchanged A inputs; never pretend it validates B.
- **Convergence at meaningful joins, without polling:** on coherent lot completion, decisive reviewer evidence, material regression or before another final review, compare the SAME contract/root-cause family against its previous checkpoint. Examine newly demonstrated vs invalidated DoD criteria, newly proved/resolved/reopened mandatory findings, discriminating positive/negative evidence and fingerprint, failed strategy hypotheses, and growth in bespoke complexity. Record only changed facts plus `CONTINUE | REPLAN | ESCALATE/HOLD` and next action in the existing Beads item. Preserve prior attempts across sessions; do not create a dashboard, score or new tracker. Green tests, extra commits and promises of a 'last review' alone are NOT convergence evidence.
- **Stop/replan the affected class** as soon as a demonstrated finding disproves the architectural premise, repeated proved same-root counterexamples survive local green tests, OR two genuinely distinct strategies fail. Count a strategy by its underlying mechanism/hypothesis: adding regex exceptions, guard syntax branches or more tests to the same heuristic is NOT a different strategy. Stop edits and repeated final-review retries on that class, keeping independent safe work moving. Coordinator asks the existing planner OR guardian for ONE bounded root-cause/options assessment, or uses already decisive evidence; at most a small isolated, non-mutating discriminating probe is allowed during the pause. Resume product edits ONLY after an explicit coordinator decision for a materially different mechanism or justified bounded-domain path with a falsifiable assumption and a contrasting test. No reset by renaming defects, opening another session or obtaining another reviewer opinion.
- **Value/complexity arbitration:** before extending a bespoke C parser, preprocessor/guard classifier or similar glue, compare native/compiler-backed mechanisms, simpler structure and explicit contract-compatible supported-domain limitations against representative real use cases, maintenance cost and changed supported coverage (R20/R26). A named refusal is acceptable only where the approved contract permits it; do not quietly exclude mandatory supported cases. If no proportionate in-scope solution is supported, mark affected acceptance evidence `NOT_DEMONSTRATED`, ask the owner for a concrete architecture/scope decision, and HOLD or deliver a clearly blocked draft. Do not request reviewer consensus or silently keep patching.

## 4. Test scheduling and evidence
- Developer may run **focused** tests freely within its owned isolated worktree, after completing coupled changes. For C generator type/call/assertion changes require emitted C shape + **real C/Unity/Ceedling compilation** + correct-SUT and where material faulty-SUT *behaviorally discriminating* execution. Never mistake a passing text assertion for a valid C oracle, or a mock provider for a real model call. Apply AP-01/02/03 state/real-environment contrasts where relevant.
- Coordinator schedules **one owner** for applicable full pytest/Docker/qualification profiles on an **integrated stable candidate**, not on every small patch. Use a native background Bash task for a single long command, `task-runner` for truly independent multi-step work. Reviewer, challenger, guardian and keeper NEVER rerun full campaigns. Record exact command, real exit status, version/profile, artifacts and effective code/test/config including tracked + untracked inputs. For lengthy tests isolate a committed/snapshotted worktree OR pause edits of consumed inputs, and compare fingerprints before AND after: evidence is STALE if inputs changed. A green output alone is not proof.
- Reuse exact existing evidence when relevant code/test/config/environment and assumptions are unchanged; targeted checks after corrections, then one applicable integrated campaign at convergence. Documentation/Beads/PR metadata-only edits do not invalidate unaffected executable evidence. Coordinator alone decides which tests are needed and who owns their execution; worker outputs never authorize another worker to launch them.
- Join all **required** completed reports and jobs at one meaningful integration checkpoint. Optional late reports may be unavailable; a new proven mandatory regression reopens ONLY affected work/evidence. If required work is blocked, do not falsely declare READY.

## 5. Final gate, publication and stop
- Coordinator audits true merge-base diff, scope/complexity, source and test fingerprints, Beads criterion→evidence (or NOT_DEMONSTRATED) and material PR feedback. Freeze a candidate and trigger **ONE fresh isolated non-Team `contract-reviewer`** with `/verify-feature` OR equivalent direct agent, never both by default. Give candidate fingerprint and compact source evidence; require prompt `READY|CHANGES_REQUIRED|NOT_VERIFIED` verdict and critical contrasts, not exhaustive exploration. One bounded fallback if the first produced no usable report; no unbounded resume. If materially corrected under a viable strategy, refreeze and obtain one new final review for READY; reuse unaffected test evidence. A repeated proved blocker from the same failing root class instead triggers REPLAN first: no automatic patch → final-review loop on the same mechanism.
- The coordinator independently decides `PUBLISH_READY|PUBLISH_DRAFT|HOLD`. Review opinion is advisory, not veto; an objectively disproved objection may be rejected, but a **confirmed mandatory defect, missing mandatory proof or missing usable independent final review** prevents READY. Keep named residual limitations and reasons. Enforce one substantive disposition per finding; no circular appeals among agents.
- Only coordinator writes/updates Beads/worklog, reviews PR hygiene for credentials/private paths, integrates and publishes/updates the SAME PR for PR_RECHECK. Batch routine commits/exports. Check real short CI status as applicable; CI is not a substitute for local evidence and may be skipped only on explicit owner instructions. **Never merge or start the next milestone without explicit user authorization.** Stop after PR delivery, join/cancel required jobs, shut down teammates and report actual URL/head/checks/dispositions/gaps. Do not claim a hook or agent automatically executed a task unless it actually did.

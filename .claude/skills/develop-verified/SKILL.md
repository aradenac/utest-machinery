No product/router/application verbose logging; versioned worklog remains mandatory. Work locally, ask before installing outside the repo. Do not assume Agent Teams is active or model routing succeeded: check availability and report limitations.

1. Do not overwrite user changes. Distinguish NEW_FEATURE (approved current milestone only) from PR_RECHECK (same open PR; no new feature or PR). Ensure appropriate permissions and environment; no secret or private route in outputs. Establish a concise requirement/invariant/acceptance contract with explicit executable evidence methods and a minimal change strategy BEFORE coding. Do not confuse tests green with the acceptance gate.

2. PARALLEL TEAM (early): In interactive sessions with CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1, start exactly two named, addressable teammates using .claude/agents/implementation-reviewer.md and .claude/agents/evidence-keeper.md. Start implementation while both inspect; don't wait for a first finding. Reviewer reads stable baseline then named checkpoints (base/head/hash) to avoid racing partial writes. If Teams is unavailable, use sequential fresh review and let lead own evidence; disclose degraded parallelism, never simulate native messaging.

3. DEVELOP / RECHECK: Make the smallest SUFFICIENT maintainable change under approved contracts and existing architecture. Independently reproduce each material PR finding, identify its underlying violated invariant and neighboring contrasted/mixed cases, implement and test the general fix, classify RESOLVED/PARTIAL/UNRESOLVED/NOT_VERIFIED/DISPUTED with evidence. For a new milestone, implement the complete user-visible feature (not artificially split). Detect divergence between docs, arbitration, Beads and changed main; surface genuine scope arbitration. Keep source C/SDD/oracles immutable. Run useful tests locally and real WSL/Docker/LLM integration when AP-02 requires it; mocks cannot prove a real call. No feature or source change to silence a review. Send stable revision IDs, exact commands/outcomes and reviewer dispositions to keeper in compact messages.

4. CONVERGENCE CONTROL: Automatically invoke a fresh unnamed convergence-guardian subagent after the plan, on major architecture/scope/diff changes, after repeated unsuccessful corrections or disagreement, and before PR publication. It audits approved scope vs base-to-head diff, unnecessary abstractions, redundant tests, and stalled progress; returns grounded minimal actions rather than edits. The lead tests/refutes findings; do not rubber-stamp or let the guardian create requirements. Do not spawn a continuously polling guardian. If the same failing check/finding recurs without new evidence, stop the unproductive loop: revisit the contract, seek a different cause/strategy, then continue or report a blocker. Aim for minimum justified DIFF, not minimum lines or omitted necessary tests/docs.

5. LONG COMMANDS VS INDEPENDENT TASKS — CHOOSE THE LIGHTEST CONCURRENCY:
- First ask: while this operation runs, can the lead make useful progress on DIFFERENT work without depending on its result, and without shared-write/input races? Do not create artificial work to justify parallelism.
- SHORT / prerequisite command: execute normally. LONG straightforward command (test/build/install/probe/etc.): use Claude Code native Bash `run_in_background` / task ID by default, even when no teammate is warranted. Continue useful independent work if possible; otherwise await completion. Retrieve the actual exit/status/output before using the result; background launch is NOT acceptance.
- Only for a LONG, BOUNDED, AUTONOMOUS task with genuine independent overlap AND meaningful multi-step execution/investigation/diagnosis beyond a single command: optionally delegate to ONE background `task-runner` subagent via .claude/agents/task-runner.md when a final report suffices; use a named Agent Teams teammate only when interim messaging or coordination is truly necessary. Examples: sequenced integration campaign, bounded independent investigation, multi-command environment analysis, build qualification. Do NOT delegate just to have another agent watch a shell process or duplicate reviewer/keeper roles. No continuously polling worker. If Agent Teams is unavailable, an ordinary background subagent may still be used if available; otherwise use background Bash. Never fake parallelism.
- For either mode, prevent conflicting writes and stale inputs. Use stable revision/file hashes; snapshot only when inputs may change while the task executes. A commit/worktree is one option, not a universal prerequisite: an explicitly captured copy may include relevant uncommitted files. Use separate scratch outputs/containers; do not modify tracked product files from the worker. Lead remains sole implementer and can change independent files, but must invalidate/re-execute affected checks on the final candidate.
- Synchronize all mandatory background task IDs and delegated results before evidence/final review; record observed outcomes and exact input versions with the keeper (exclusive Beads/worklog writer). Failed, blocked or obsolete mandatory work cannot be treated as passing. Respect host/secret boundaries and resource limits; no new daemon, result tracker, CI job or automatic merge.

Sanitize credentials, personal data and private host paths per AP-05. If any applicable mandatory criterion is NOT_DEMONSTRATED, mark BLOCKED, never READY.

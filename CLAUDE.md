## Single-entry verified development

For one approved milestone or substantive correction on an existing PR, invoke **`/develop-verified` once**. The MAIN conversation is the **coordinator**, not the developer: it translates approved DoD into coherent Beads lots, assigns specialist missions, owns priorities and joins, schedules full tests on stable inputs, arbitrates independent findings, conducts one bounded final `/verify-feature` review, and alone publishes the PR. The `developer` subagent owns implementation and targeted tests; a `planner` may propose decomposition/replanning when useful; reviewer, test-challenger, guardian, runner and keeper are conditional/advisory. One developer is the default; parallel writers require disjoint worktrees and outputs. Never create a serial reviewer barrier per slice.

**Coordinator-only communication:** specialists return evidence/messages to the coordinator and do not message each other, reassign tasks or write the shared Beads backlog. The developer is autonomous over technical corrections and may substantively reject weak reviewer assertions, but only the coordinator changes backlog priorities or publication status, and neither can waive a proven mandatory criterion. Beads holds durable execution; native Tasks optionally model in-session dependencies. A reviewer reports fingerprint-bound findings to the coordinator, which groups root causes into lots and interrupts a developer only when necessary; one early challenge for material correctness risks. No unbounded review/retry loops.

**Agent monitoring:** project-level `TeammateIdle` in `.claude/settings.json` applies in teammate sessions that load project settings; session-scoped `SubagentStop`, `TaskCompleted` and `Stop` come from `/develop-verified`. All use `.claude/hooks/develop-verified.py` for *mechanical* checks. An optional ignored, Team-name-scoped active mission receipt lets `TeammateIdle` request one missing fingerprint-bound report before allowing idle; `TaskCompleted` still checks optional `Proof-file:`, `SubagentStop` requests one missing short handback and `Stop` prevents a literal READY claim with background tasks active. A missing notification/IDLE is **not failure**: coordinator checks the report and native agent/task state at useful joins, sends at most one bounded retry, then uses a necessary isolated fallback or reports NOT_VERIFIED. Hooks do not poll stalled workers, launch agents/tests or provide OS-level enforcement; verify availability under actual CCR/Claude Code.

**Evidence and release:** developer runs focused, discriminating tests; coordinator alone schedules one full campaign via native background Bash or a designated isolated task-runner on a stable integrated candidate. Capture true command exit, environment and effective code/test/config hashes before AND after; mark changed inputs STALE and reuse unaffected evidence instead of reruns. Mandatory AP-01/02/03/04/05 and C generator compilation/behavioral-oracle gates remain. One fresh isolated, bounded final contract-reviewer (even docs-only) is advisory: coordinator ACCEPT/REJECT/DEFER material findings on proof and chooses `PUBLISH_READY|PUBLISH_DRAFT|HOLD`. Missing mandatory evidence or independent final review blocks READY. **No automatic merge or next milestone**.

## Start of every development session

1. Inspect `git status`, current branch, merged PRs, code and existing checks. Reconcile the documented feature milestones with **what has actually merged**. Never infer completion from a checklist alone.
2. Check Beads (`bd prime`, `bd ready`, `bd list`). Initialize only if absent (`bd init --skip-agents`; pin/check version); preserve the repository's instructions. **Reconcile** backlog, dependencies and comments with the plan, PRs and evidence. `docs/plan/implementation.md` is the scope authority; Beads tracks execution, not a second product specification.
3. Select **only the next approved feature milestone**. Coordinate its implementation, relevant local tests and evidence; update Beads status; open **one PR** with evidence (review-ready if objectively demonstrated, otherwise optionally **draft** with explicit unverified criteria/known blockers at the coordinator's discretion). **STOP after opening the PR. Do not merge, start another milestone or continue automatically.** Wait for review and an explicit instruction before proceeding.
4. On a subsequent session, inspect **new or materially outstanding** feedback on the **same open PR** and prior recorded dispositions, critically assess every substantive finding, rerun only invalidated checks and let the coordinator invoke one bounded `/verify-feature` in PR_RECHECK mode before re-requesting review. Keep the correction status and evidence in the existing Beads item; stop again. Only after an externally merged PR and a new user instruction may you start the next milestone.

## Working record (`worklog/`) — mandatory

Maintain a versioned working record under [`worklog/`](worklog/README.md). This is the agent's own log, **not** product documentation; do not add or restructure content under `docs/`, and if a note ever contradicts a `docs/` page, `docs/` wins.

- **Log every session** in `worklog/log/YYYY-MM-DD.md` (suffix if a second session the same day): what was inspected, what was done, what was observed, actions taken, files touched, results, and what is next.
- **Trace every decision** as a numbered record in `worklog/decisions/NNNN-slug.md` (context, options considered, decision, status, consequences, references). Once decided, supersede rather than rewrite and cross-link the superseding ID.
- **Record risks, limitations, arbitration and history** as they arise: open questions and arbitrations in `worklog/questions.md`, answered ones moved to the dated log with the resolution and date; residual risks and limitations in the relevant decision record or log entry.
- **Update before stopping**, in the same PR/branch as the work: a session, a decision, a failure or a result that is not in `worklog/` did not happen as far as review is concerned.
- Distinguish **observed facts** from **inferences/claims**; pin exact versions/tags/digests; never write a secret — reference a variable name and do presence checks only.

## Working rules

- Read the [risk register](docs/project/risks.md) as context, **but never edit it** (including risk scores, statuses or mitigation actions). Risk reassessment belongs to an independent review.
- **Working record and instruction sync (AP-04):** keep `worklog/` as detailed chronological agent memory (attempts, failures, observations), **Beads** as concise final decisions/alternatives and acceptance evidence, the **PR** as delivered changes, test results and links to Beads, and `docs/` as normative product requirements. Before publishing or refreshing a PR, compare applicable instructions on current `main` with the feature branch and reconcile changes without losing the worklog protocol. Do not create another backlog or duplicate the evidence.
- **Complexity watch (R20):** make routine implementation decisions autonomously. Before significant new glue, wrappers, custom engines or duplicate data models, check existing tool capabilities, simpler integrations and whether the requirement can be fulfilled with less complexity. For a nontrivial choice, add a **brief justification in the relevant Beads item/comment**, covering the chosen option, meaningful alternatives and maintenance trade-off; do not produce a separate architecture report or duplicate this rationale in the PR. Keep Beads notes synchronized/versioned so reviewers can inspect them; the PR only references the corresponding Beads IDs.
- If the simplest workable design is still disproportionate to its feature value, **flag the concern and recommended alternatives to the user before committing to a scope or major architecture change**. Do not silently drop requirements or assume permission to change scope.

- Work inside the repository and local virtual environments/container. Ask before installing anything outside the project or modifying host system settings.
- Input C, headers, SDDs and other selected artifacts are immutable. Product-specific files are in one external test-bench directory; do not modify application source or silently adjust an SDD-derived oracle.
- Run **all relevant tests locally first**. Coordinator designates exactly one executor for complete pytest/build/Docker campaigns (a task-runner or one coordinator-owned native background Bash job); developer owns only scoped targeted tests. Use targeted regressions after each fix, and full applicable suites on stable candidates; reuse same-revision/configuration results, rerun invalidated checks and avoid duplicate suite execution by reviewers/guardian/keeper. For straightforward long commands use native background Bash, reserving `task-runner` for truly independent multi-step work. Join results, record exact commands, true exit codes, revisions/hashes and artifacts before readiness (a piped grep summary without pipefail is not test success). CI is the short independent reproducibility gate, **not your debugging environment**.
- **Acceptance evidence (AP-01):** before declaring a feature PR review-ready OR publishing a clearly labeled draft, check **every applicable acceptance criterion** of the current milestone against a test/command actually executed and its observed result. Record a concise **criterion → evidence** reference (command/result/log or artifact), or explicitly mark it **NOT_DEMONSTRATED** with the reason, in the relevant **Beads feature item/comment**; the PR links Beads and reports real test results instead of duplicating a matrix. A mandatory unproven criterion is a **review-readiness blocker** even if CI is green; the coordinator may publish a **draft** with explicit unresolved evidence/limitations for collaboration but cannot claim readiness or authorize merge.
- **After PR review findings (AP-01):** identify the **general contract/invariant violated** by each finding, fix the observed case and test the **relevant neighboring or contrasting cases** that could exhibit the same defect. Record the additional evidence or remaining limits in Beads before re-requesting review. Keep these checks proportional to the current milestone; do not create unrelated tests, tools or a second tracking system.
- **Independent feature verification (AP-01/AP-03):** invoke the project `/verify-feature` skill using `.claude/agents/contract-reviewer.md` in a **fresh isolated subagent context**. **PRE_PR:** after relevant local tests and before claiming a feature PR ready, pass the milestone and base/head (not a leading list of desired findings); the verifier derives its own contract counterexamples. **PR_RECHECK:** when a PR is already open and substantive review findings have been corrected, pass its **PR number/URL** and request verification of **all material review feedback**, each underlying contract, the fixes since the reviewed revision and adjacent regressions; do not just repeat the developer's claimed resolutions. The verifier reads review bodies/inline comments/discussion, returns an evidence-led status for each finding plus any new blockers, and **does not edit tracked code or Beads**. The developer provides an independent technical disposition and evidence to the coordinator, which **ACCEPTs, REJECTs or DEFERs** each material critique for scheduling/publication: a confirmed mandatory violation must be resolved or the candidate marked incomplete, whereas a falsified, speculative or extra-scope claim may be rejected with contractual justification. The coordinator alone decides publication mode, delegates necessary targeted regressions, records the compact outcome in the **same Beads feature item**, and updates that same PR; no second report/tracker. Run one bounded full PRE_PR review and one targeted PR_RECHECK for each **materially changed effective candidate/contract**. Docs-only changes within `/develop-verified` are NOT exempt, but worklog/Beads export/PR-text updates that do not alter normative contracts or executable inputs do not invalidate already verified code, tests or review findings. Invoke `/verify-feature` OR one direct equivalent, not both; if the chosen invocation returns no structured verdict, make at most one fallback requesting an immediate partial report. Do not re-run full suites to recover an LLM report. After two failed distinct correction strategies on the same defect class, stop local loops and escalate without waiving mandatory defects. If the reviewer cannot retrieve PR comments or delegation is unavailable, mark relevant checks `NOT_DEMONSTRATED` rather than assume success. Neither mode replaces external PR review.
- **Critical invariants (AP-03):** when a feature persists/changes state or converts technical states/results into user-facing verdicts, identify its **few critical invariants** and verify the relevant **transitions and contrasting/mixed outcomes**. Examples when applicable: write → read; failure → repeated status consultation; reset/update → preserve unaffected data; interrupt → resume; RUNNING ≠ failure; test finding + tool failure must not hide the tool failure. Validate persistent schemas at both read and write boundaries. **Record each applicable invariant and its executed test/result (or `NOT_DEMONSTRATED` with reason) in the existing AP-01 Beads evidence**; a mandatory invariant left unproven blocks readiness. Avoid exhaustive transition matrices, new frameworks, extra commands or checks for unrelated future milestones.
- **Real-environment integration (AP-02):** when a milestone crosses installation, Docker, runner, compiler or LLM boundaries, execute **at least one representative end-to-end user CLI path in its intended host/WSL and container environment**, to an observable result. Use the **actually installed artefact** when packaging matters; verify minimal host prerequisites, scoped mounts/ownership and an attempted denied write to original inputs when applicable. Record exact commands, observed results and any unsupported/unproven link in the existing AP-01 Beads evidence/PR. A mandatory path not demonstrated blocks readiness; do not repeat costly integration tests for every unit or add a new harness.
- **Prepublication hygiene (AP-05):** before committing or publishing a PR, inspect added/changed tracked files and relevant logs/artefacts (including `worklog/`, Beads export and generated outputs) for credentials/tokens, personal identifiers, private host paths or unnecessary internal gateway/topology details. Remove or sanitize them, preferring environment-variable names and generic examples. Reuse existing diff/review controls; no new scanner, governance system or credential copies in the repository.
- Each PR implements a complete user-visible capability with its fixtures, necessary failure cases, updated docs/diagram and exact test commands/results. Do not split a feature into artificial PRs.
- Never fabricate a test result, tool metric, mutation outcome, target-MCU guarantee or implementation status. Distinguish a detected product-code defect from a broken test harness.
- Honor the [error/stop contract](docs/architecture/workflow-failures.md). A failed selected unit does not imply aborting independent checks; a broken workflow/infrastructure cannot report success.
- Product's **initial LLM configuration is Claude Code + Claude Code Router (CCR) + DeepSeek V4.1 Flash**. Do not replace it with a generic multi-provider framework. See [developer setup](docs/development/setup.md); credentials always outside repo/image.
- Only free deterministic test tools. Dagu is the preferred text-defined/headless runner pending a real gate test. QEMU/Renode are later, separate scope.
- No GitHub issues required for planning. Use **Beads (`bd`)** for the developer backlog: one feature milestone per major work item, optional implementation subtasks, comments and dependencies. Before PR: export the current Beads issue view to `.beads/issues.jsonl` for Git review, and sync the Dolt state according to the pinned version's docs. **JSONL is not a full Dolt backup**; never claim otherwise. Exclude local DB/cache/secrets from ordinary source commits.
- Use the [PR template](.github/PULL_REQUEST_TEMPLATE.md) with exact local checks, fast CI results, Beads IDs and remaining risks.

## Completion rule

The **coordinator** is accountable for deciding publication status, not obliged to seek consensus from subagents. The milestone is **ready for review** only when mandatory acceptance methods have been executed or otherwise evidenced as required, all genuine mandatory defects are resolved, limitations are documented, the PR contains reproducible evidence, and Beads reflects the actual PR state. If these conditions are not yet met, the coordinator may still publish the work as a clearly marked **draft** with accurate blockers/unverified evidence; publication is not acceptance or permission to merge. Its status remains `in_progress`/under review until the PR is merged. Then **stop**; do not start the next milestone without authorization.

## Single-entry verified development

For a new approved milestone or substantive corrections on the same open PR, invoke `/develop-verified` **once**. Its versioned entry point (`.claude/skills/develop-verified/SKILL.md`) defines a finite acceptance contract, lets the **lead implement without a mandatory plan-review barrier**, starts a risk-focused oracle/test challenge early when warranted, selects targeted then stable-candidate full tests, runs **one** fresh bounded independent `/verify-feature` review, and supports lead-owned PR/CI delivery. The optional plan reviewer, live implementation reviewer, convergence guardian and evidence keeper are **conditional**, not default release gates; Agent Teams is optional. Native background Bash handles individual slow commands without extra polling agents. Do not ask the user for a separate verifier prompt.

The approved milestone determines scope and DoD; the lead dynamically chooses **coherent implementation slices**, optionally tracked as native Claude Code Tasks (not mandatory Beads subtickets). Critics can challenge stable slice snapshots **in parallel** while the lead works on independent scopes; integration joins their substantive reports before the final full suite/reviewer. Parallel code writers are optional only with disjoint worktrees/files and explicit ownership; no competing PR/Beads/worklog or shared build-directory writers. Never turn every slice into a serial approval gate. Before repeatedly patching a **shared invariant**, inspect its direct consumers and a few representative neighboring categories; a decisive proven critic finding should be surfaced early, not held for an exhaustive report.

The `/develop-verified` skill registers session-scoped `SubagentStop`, `TaskCompleted` and `Stop` **command hooks** for narrow delivery checks, not semantic acceptance decisions. The subagent hook requests a substantive summary only if absent (one bounded continuation); an optional `Proof-file: path` in a native Task description checks a declared local artifact; the stop hook catches `PUBLISH_READY` asserted with work still in the background. None runs test suites or implies automatic approval. See [developer setup](docs/development/setup.md).

The lead is the technical decision-maker: independently ACCEPT/REJECT/DEFER material reviewer claims with evidence. Independent review on every `/develop-verified` candidate (including docs-only) remains mandatory and advisory, not a veto. `PUBLISH_READY` still requires executed mandatory evidence and no unresolved demonstrated mandatory defect; `PUBLISH_DRAFT` or `HOLD` covers gaps. A complete review must bind to the frozen **effective candidate** (remote merge-base, code/test/config and relevant evidence hashes, material PR comments), not just green CI. A full campaign needs **stable effective inputs throughout its run** (isolated snapshot/worktree or no overlapping input edits), plus before/after fingerprints and the true command exit; a green run on changing inputs is stale. Worklog/Beads/PR metadata-only changes do not invalidate unchanged code/test results or mandate a new full campaign. One fallback is allowed if the verifier invocation produces no usable report; avoid repeated resumes or duplicate independent reviewers.

The lead owns tests, source and PR; it also owns Beads/worklog by default. For substantial independent record-writing only, delegate to an evidence keeper with explicit ACK/ACCEPTED and RELEASED/confirmed termination before any takeover. Critics are read-only and never repeat whole qualification campaigns. Treat native messages as optional hints; inspect completed reports at a meaningful join point instead of repeatedly polling. Guardian runs only for demonstrable drift/stalls, and test-challenger runs **early** for material oracle/behavior risks, never as a late surprise after the full suite. Preserve the existing AP-01/02/03/04/05 evidence contracts, project scope, exclusive writer rules and no-auto-merge boundary.

## Start of every development session

1. Inspect `git status`, current branch, merged PRs, code and existing checks. Reconcile the documented feature milestones with **what has actually merged**. Never infer completion from a checklist alone.
2. Check Beads (`bd prime`, `bd ready`, `bd list`). Initialize only if absent (`bd init --skip-agents`; pin/check version); preserve the repository's instructions. **Reconcile** backlog, dependencies and comments with the plan, PRs and evidence. `docs/plan/implementation.md` is the scope authority; Beads tracks execution, not a second product specification.
3. Select **only the next approved feature milestone**. Complete its implementation, tests and local verification; update Beads status; open **one PR** with evidence (review-ready if objectively demonstrated, otherwise optionally **draft** with explicit unverified criteria/known blockers at the lead's discretion). **STOP after opening the PR. Do not merge, start another milestone or continue automatically.** Wait for review and an explicit instruction before proceeding.
4. On a subsequent session, inspect **new or materially outstanding** feedback on the **same open PR** and prior recorded dispositions, critically assess every substantive finding, rerun only invalidated checks and let `/develop-verified` invoke one bounded `/verify-feature` in PR_RECHECK mode before re-requesting review. Keep the correction status and evidence in the existing Beads item; stop again. Only after an externally merged PR and a new user instruction may you start the next milestone.

## Working record (`worklog/`) — mandatory

Maintain a versioned working record under [`worklog/`](worklog/README.md). This is the agent's own log, **not** product documentation; do not add or restructure content under `docs/`, and if a note ever contradicts a `docs/` page, `docs/` wins.

- **Log every session** in `worklog/log/YYYY-MM-DD.md` (suffix if a second session the same day): what was inspected, what was done, what was observed, actions taken, files touched, results, and what is next.
- **Trace every decision** as a numbered record in `worklog/decisions/NNNN-slug.md` (context, options considered, decision, status, consequences, references). Once decided, supersede rather than rewrite and cross-link the superseding ID.
- **Record risks, limitations, arbitration and history** as they arise: open questions and arbitrations in `worklog/questions.md`, answered ones moved to the dated log with the resolution and date; residual risks and limitations in the relevant decision record or log entry.
- **Update before stopping**, in the same PR/branch as the work: a session, a decision, a failure or a result that is not in `worklog/` did not happen as far as review is concerned.
- Distinguish **observed facts** from **inferences/claims**; pin exact versions/tags/digests; never write a secret — reference a variable name and do presence checks only.

## Working rules

- Read the [risk register](docs/project/risks.md) as context, **but never edit it** (including risk scores, statuses or mitigation actions). Risk reassessment belongs to an independent review.
- **Working record and instruction sync (AP-04):** keep `worklog/` as detailed chronological agent memory (attempts, failures, observations), **Beads** as concise final decisions/alternatives and acceptance evidence, the **PR** as delivered changes, test results and links to Beads, and `docs/` as normative product requirements. Before publishing or refreshing a PR, compare applicable instructions on current `main` with the feature branch and reconcile changes without losing the worklog protocol. Do not create another backlog or duplicate the evidence.
- **Complexity watch (R20):** make routine implementation decisions autonomously. Before significant new glue, wrappers, custom engines or duplicate data models, check existing tool capabilities, simpler integrations and whether the requirement can be fulfilled with less complexity. For a nontrivial choice, add a **brief justification in the relevant Beads item/comment**, covering the chosen option, meaningful alternatives and maintenance trade-off; do not produce a separate architecture report or duplicate this rationale in the PR. Keep Beads notes synchronized/versioned so reviewers can inspect them; the PR only references the corresponding Beads IDs.
- If the simplest workable design is still disproportionate to its feature value, **flag the concern and recommended alternatives to the user before committing to a scope or major architecture change**. Do not silently drop requirements or assume permission to change scope.

- Work inside the repository and local virtual environments/container. Ask before installing anything outside the project or modifying host system settings.
- Input C, headers, SDDs and other selected artifacts are immutable. Product-specific files are in one external test-bench directory; do not modify application source or silently adjust an SDD-derived oracle.
- Run **all relevant tests locally first**. Lead (or explicitly delegated task-runner) is the sole owner of complete pytest/build/Docker campaigns. Use targeted regressions after each fix, and full applicable suites on stable candidates; reuse same-revision/configuration results, rerun invalidated checks and avoid duplicate suite execution by reviewers/guardian/keeper. For straightforward long commands use native background Bash, reserving `task-runner` for truly independent multi-step work. Join results, record exact commands, true exit codes, revisions/hashes and artifacts before readiness (a piped grep summary without pipefail is not test success). CI is the short independent reproducibility gate, **not your debugging environment**.
- **Acceptance evidence (AP-01):** before declaring a feature PR review-ready OR publishing a clearly labeled draft, check **every applicable acceptance criterion** of the current milestone against a test/command actually executed and its observed result. Record a concise **criterion → evidence** reference (command/result/log or artifact), or explicitly mark it **NOT_DEMONSTRATED** with the reason, in the relevant **Beads feature item/comment**; the PR links Beads and reports real test results instead of duplicating a matrix. A mandatory unproven criterion is a **review-readiness blocker** even if CI is green; the lead may publish a **draft** with explicit unresolved evidence/limitations for collaboration but cannot claim readiness or authorize merge.
- **After PR review findings (AP-01):** identify the **general contract/invariant violated** by each finding, fix the observed case and test the **relevant neighboring or contrasting cases** that could exhibit the same defect. Record the additional evidence or remaining limits in Beads before re-requesting review. Keep these checks proportional to the current milestone; do not create unrelated tests, tools or a second tracking system.
- **Independent feature verification (AP-01/AP-03):** invoke the project `/verify-feature` skill using `.claude/agents/contract-reviewer.md` in a **fresh isolated subagent context**. **PRE_PR:** after relevant local tests and before claiming a feature PR ready, pass the milestone and base/head (not a leading list of desired findings); the verifier derives its own contract counterexamples. **PR_RECHECK:** when a PR is already open and substantive review findings have been corrected, pass its **PR number/URL** and request verification of **all material review feedback**, each underlying contract, the fixes since the reviewed revision and adjacent regressions; do not just repeat the developer's claimed resolutions. The verifier reads review bodies/inline comments/discussion, returns an evidence-led status for each finding plus any new blockers, and **does not edit tracked code or Beads**. The developer **independently accepts, rejects or defers** each material critique: a confirmed mandatory violation must be resolved or the candidate marked incomplete, whereas a falsified, speculative or extra-scope claim may be rejected with contractual justification. The lead alone decides publication mode, executes any necessary targeted regressions, records the compact outcome in the **same Beads feature item**, and updates that same PR; no second report/tracker. Run one bounded full PRE_PR review and one targeted PR_RECHECK for each **materially changed effective candidate/contract**. Docs-only changes within `/develop-verified` are NOT exempt, but worklog/Beads export/PR-text updates that do not alter normative contracts or executable inputs do not invalidate already verified code, tests or review findings. Invoke `/verify-feature` OR one direct equivalent, not both; if the chosen invocation returns no structured verdict, make at most one fallback requesting an immediate partial report. Do not re-run full suites to recover an LLM report. After two failed distinct correction strategies on the same defect class, stop local loops and escalate without waiving mandatory defects. If the reviewer cannot retrieve PR comments or delegation is unavailable, mark relevant checks `NOT_DEMONSTRATED` rather than assume success. Neither mode replaces external PR review.
- **Critical invariants (AP-03):** when a feature persists/changes state or converts technical states/results into user-facing verdicts, identify its **few critical invariants** and verify the relevant **transitions and contrasting/mixed outcomes**. Examples when applicable: write → read; failure → repeated status consultation; reset/update → preserve unaffected data; interrupt → resume; RUNNING ≠ failure; test finding + tool failure must not hide the tool failure. Validate persistent schemas at both read and write boundaries. **Record each applicable invariant and its executed test/result (or `NOT_DEMONSTRATED` with reason) in the existing AP-01 Beads evidence**; a mandatory invariant left unproven blocks readiness. Avoid exhaustive transition matrices, new frameworks, extra commands or checks for unrelated future milestones.
- **Real-environment integration (AP-02):** when a milestone crosses installation, Docker, runner, compiler or LLM boundaries, execute **at least one representative end-to-end user CLI path in its intended host/WSL and container environment**, to an observable result. Use the **actually installed artefact** when packaging matters; verify minimal host prerequisites, scoped mounts/ownership and an attempted denied write to original inputs when applicable. Record exact commands, observed results and any unsupported/unproven link in the existing AP-01 Beads evidence/PR. A mandatory path not demonstrated blocks readiness; do not repeat costly integration tests for every unit or add a new harness.
- **Prepublication hygiene (AP-05):** before committing or publishing a PR, inspect added/changed tracked files and relevant logs/artefacts (including `worklog/`, Beads export and generated outputs) for credentials/tokens, personal identifiers, private host paths or unnecessary internal gateway/topology details. Remove or sanitize them, preferring environment-variable names and generic examples. Reuse existing diff/review controls; no new scanner, governance system or credential copies in the repository.
- Each PR implements a complete user-visible capability with its fixtures, necessary failure cases, updated docs/diagram and exact test commands/results. Do not split a feature into artificial PRs.
- Never fabricate a test result, tool metric, mutation outcome, target-MCU guarantee or implementation status. Distinguish a detected product-code defect from a broken test harness.
- Honor the [error/stop contract](docs/architecture/workflow-failures.md). A failed selected unit does not imply aborting independent checks; a broken workflow/infrastructure cannot report success.
- Product's **initial LLM configuration is Claude Code + Claude Code Router (CCR) + DeepSeek V4.1 Flash**. Do not replace it with a generic multi-provider framework. See [developer setup](docs/development/setup.md); credentials always outside repo/image.
- Only free deterministic test tools. Dagu is the preferred text-defined/headless runner pending a real gate test. QEMU/Renode are later, separate scope.
- No GitHub issues required for planning. Use **Beads (`bd`)** for the developer backlog: one feature milestone per major work item, optional implementation subtasks, comments and dependencies. Before PR: export the current Beads issue view to `.beads/issues.jsonl` for Git review, and sync the Dolt state according to the pinned version's docs. **JSONL is not a full Dolt backup**; never claim otherwise. Exclude local DB/cache/secrets from ordinary source commits.
- Use the [PR template](.github/PULL_REQUEST_TEMPLATE.md) with exact local checks, fast CI results, Beads IDs and remaining risks.

## Completion rule

The **lead** is accountable for deciding publication status, not obliged to seek consensus from subagents. The milestone is **ready for review** only when mandatory acceptance methods have been executed or otherwise evidenced as required, all genuine mandatory defects are resolved, limitations are documented, the PR contains reproducible evidence, and Beads reflects the actual PR state. If these conditions are not yet met, the lead may still publish the work as a clearly marked **draft** with accurate blockers/unverified evidence; publication is not acceptance or permission to merge. Its status remains `in_progress`/under review until the PR is merged. Then **stop**; do not start the next milestone without authorization.

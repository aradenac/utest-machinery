## D6 — what the user must provide (explained)

In plain terms, for the in-image Claude Code + CCR to route to `deepseek-v4.1-flash` exactly
like the host does, I need **four non-secret pieces of information** about the working host
route (never the token itself), because the host stores its CCR config in `config.sqlite`
rather than a readable `config.json`:

1. **The provider/route name and type** the host uses (e.g. a custom OpenAI-compatible
   provider pointing at the Scaleway gateway), as it appears in the router UI/config.
2. **The exact upstream base URL** shape the container should call. The host uses
   `SCW_BASE_URL`; I need to know whether the container should use the **same** URL (i.e.
   whether it is reachable from inside Docker) or an internal alias.
3. **The exact model identifier** the router sends upstream (`deepseek-v4.1-flash` — confirm
   spelling) and the **API surface** (OpenAI `/chat/completions` vs Anthropic `/v1/messages`).
4. **Any non-secret headers/prefixes** the gateway expects (e.g. an API-key header name or a
   path prefix), if different from the defaults.

No secret is needed in the explanation: the token comes from
`~/.config/utest-machinery/credentials.env` (or a runtime secret mount) at execution time and
is never copied into the image, Git or logs.

## Session 1 (continued 5) — PR #5 review, round 3 (six blockers)

A third review pass raised six blocking comments. All six are implemented, tested and
verified locally.

1. **False `INTERRUPTED` for active Docker runs** (`mtm/engine.py`). The docker path passed
   `pid=0`, and `_finalize` treated "no host PID" as "dead owner". Fixed by making
   `_pid_alive` return `bool | None` (`None` = not determinable, **not** reconciled) and by
   labelling the owner container `mtm.run-id=<id>`: a status query resolves liveness with
   `docker ps --filter label=...`. `RunStatus` now carries `owner_alive` + `liveness_evidence`.
   → [`decisions/0008`](../decisions/0008-docker-liveness-and-mount-policy.md).
   New integration tests: a live container reads `RUNNING`/`owner_alive: true`; a killed
   container reconciles to `INTERRUPTED`/exit 130.
2. **Wrong failure taxonomy** (`mtm/commands.py`). Every Dagu `FAILED` mapped to
   `TEST_FINDING`/exit 10. Fixed: a step types its own outcome via an `MTM_CATEGORY` output;
   only `{TEST_FINDING, INPUT_LIMITATION, TOOL}` are honoured, everything else (and any
   untyped failure) is a **tool/workflow failure, exit 30**. → [`decisions/0007`](../decisions/0007-workflow-outcome-taxonomy.md).
   The test that expected exit 10 for `exit 3` now expects exit 30; a new test proves a typed
   `TEST_FINDING` still yields exit 10.
3. **Non-JSON `status` hid the diagnosis** (`mtm/cli.py`). `_print_human` never rendered
   `last_operation`. Now renders stage/status/code/message/cause/action in text. New CLI test
   asserts the failure is visible after one and after two queries.
4. **Wheel had no usable image build context** (`mtm/docker.py`, packaging test). Decision:
   the build context is the **source tree**, not the installed package (a wheel ships the
   control CLI + data, not a Docker context; the Dockerfile also copies `mtm/`). The contract
   is now explicit and **tested**: from outside a checkout, `mtm install` fails with exit 40 /
   `CONFIG_INVALID` and an actionable message. I considered packaging the whole context in the
   wheel and judged it disproportionate (flagged per the R20 scope rule).
5. **Broad RW bench mount** (`mtm/engine.py`). The bench was mounted RW, so a run could
   overwrite selected inputs. Now `<bench>:/bench:ro` plus `<bench>/.mtm:/bench/.mtm` RW.
   Integration test + CI smoke prove a step cannot modify a selected source.
6. **Partial `init --force` preservation** (`mtm/commands.py`). Only `scopes` were kept;
   `selectors` and unknown additive fields were reset. Now every existing field is preserved
   (`raw` copied, `selectors` kept); `--source`/`--spec` override only when explicitly passed.
   New test sets `selectors` + a custom field and asserts they survive `--force`.
